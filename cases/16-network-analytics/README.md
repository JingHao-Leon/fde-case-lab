# 案例16 · 电信网络数据分析 Agent（确定性语义层）

> 对应《Datawhale FDE 案例 100》NO.16「从人工分析到分钟级洞察」· 技术主题：语义层 / 查询规划 / 生产级 Agent 工程
> 方法论标签："能跑起来"≠"能落地"、模型随机性不能带进业务系统、答案可审计

## 业务背景（原案例）

美国头部电信运营商，分析师人工写 SQL 回答"哪个基站坏了/影响多大"，按天计；
客户自建的"提示词 Agent"（把问题直接丢给模型）同一问题两次答案不同，仪表盘
又无法支持分析师的连续追问。

## 技术问题

把分析问答做成**可反复运行的业务系统**：意图路由 → 槽位白名单 → 参数化 SQL →
结构化答案。核心验收不是"能回答"，而是：同一问题重复执行答案逐位一致、
答案附 SQL 可审计、延迟毫秒级。

## 方案（solution.py）

- `NaiveAgent`：现状基线——不做意图规划，top5 候选按哈希计数器"采样"输出，
  复现"temperature>0 的提示词 Agent"的不稳定性。
- `SemanticAgent`：确定性流水线，5 类意图（故障排名/站点状态/影响面/根因/趋势），
  站点槽位白名单（`S\d{2}` 之外不进查询层），SQL 全部常量+占位符绑定。
- 评测集：100 条真实追问风格的问题，覆盖 5 类意图 × 50 站点，内嵌 6 小时故障事件
  （S17：掉线率 0.45、告警 19 条、流量迁移）。

## 实测结果

```
Agent                    意图路由正确率   答案稳定性(5次)   命中故障站   P50延迟
朴素采样Agent(现状)              0%            0%          20%       —
确定性语义层Agent              100%          100%         100%     0.3ms
```

复现：`python cases/16-network-analytics/bench.py`

**结论**：把"模型的随机性"关进确定性流水线后，稳定性从 0% 到 100%——这正是
原案例的观点："汽油不稳定，但汽车工程让汽油安全地驱动车辆"。朴素 Agent 的
20% 命中率约等于"在 top5 里瞎猜"，而语义层每个答案都带可复查的 SQL。
局限：意图集需按业务扩展，复杂问句（多跳、对比）需要语义解析升级，
这也是"语义层 + LLM 规划"混合架构的用武之地。

## 测试

`pytest cases/16-network-analytics` 覆盖：槽位白名单、同题 10 次执行一致性、
朴素 Agent 不稳定复现（设计如此）、100 题路由正确率 ≥95、评测集两次全量执行
逐位一致、故障事实校验（S17 排名第一且告警强相关）。
